# PrayerStop — AI Development Guide

PrayerStop is a Sri Lankan Muslim mobile utility that recommends the most *practical* place to pray — combining ACJU prayer timetables, the user's location, nearby prayer places, and traffic-aware travel ETA. It is a location/time utility, not a devotional content app.

## Non-negotiable product rules

- **Never call traffic-aware routing (Google Routes) for every nearby place.** Always: discover candidates → rank locally by straight-line distance + prayer feasibility → send only a short top-N list to Routes. This is a cost/latency constraint, not a style preference.
- **Never assume the user's personal prayer status.** The app only knows the timetable and the user's selected NOW/NEXT context — copy and logic must not imply tracking of whether a prayer was performed.
- **Recommend the most reachable option, not the nearest one.** Distance alone is not the ranking signal for the final answer. Concretely (implemented Phase 5, `lib/prayer-places/build-place-scenario.ts#comparePracticality`): among candidates in the same feasibility band, prefer the closer mosque when real ETAs are similar (within 5 minutes), but prefer the significantly faster mosque when traffic has made the closer option materially slower. A single fixed threshold, not a percentage or other data-dependent comparison — keep this deterministic.
- **Unreachable results use factual language**, e.g. "Too late to reach" with arrival time vs. prayer end time — never a religious judgment. See [03-ux-and-user-flows.md](./docs/03-ux-and-user-flows.md).
- **Never fabricate a deadline or feasibility claim from data that doesn't actually support it.** Only make a "remaining time" / "too late" claim when the required timing information is genuinely available. Concretely, and permanently: **Isha's real deadline is unknown** (ACJU gives no cutoff, and we have no mosque-closing/Jama'ah data) — the next day's Fajr start is a *different prayer's* start time, not Isha's end, and must never be used as a fallback for it. This was a real, shipped bug (`active.endTime = tomorrow's Fajr` when Isha was active, producing fake "X min remaining" and false "too late" claims every night) — see `lib/prayer-times/prayer-engine.ts` and its regression tests before touching this logic again. This applies just as much to Google Places: **ordinary opening-hours / `currentOpeningHours` status does not mean a mosque is accessible for prayer** and never tells us Jama'ah timing — see [06-data-and-api-plan.md](./docs/06-data-and-api-plan.md). The one narrow exception is `businessStatus === 'CLOSED_TEMPORARILY'` — an explicit closure signal, not an opening-hours inference — which is filtered out before ranking (`lib/prayer-places/normalize-nearby-places.ts`); a place with **no** `businessStatus` at all must never be treated as closed, since missing data is not evidence of closure.
- **Never compare an arrival/leave-by time against a prayer window's bare `HH:MM` strings when the two might be on different calendar days.** This was a second, related real bug (found via Phase 5 live testing, not a hypothetical): NEXT-mode feasibility computed an arrival time from "now" and compared it directly against the *next* window's `startTime`/`endTime` strings — correct for a same-day next prayer, but silently wrong whenever the next prayer is tomorrow (e.g. evaluating late at night with NEXT = tomorrow's Fajr), since "23:50 tonight" and "04:45 tomorrow" have no notion of which calendar day they're on and a naive string/minutes-since-midnight comparison treats the later clock time as later in real time regardless. It produced a false "too late" for a scenario where hours of lead time actually remained. **Fix, and the permanent rule**: NEXT-mode feasibility must use the prayer engine's own `secondsUntilNextStart` (real elapsed seconds, already correct across midnight — see `lib/prayer-times/prayer-engine.ts`), never a fresh `HH:MM` comparison — see `lib/prayer-places/build-place-scenario.ts#classifyNextFeasibility` and its regression tests (`build-place-scenario.test.ts`, `recommendation.test.ts`) before touching this logic again. UI components must not independently recompute this either — `RecommendationHero`/`AlternatePlaceRow` had their own redundant copy of the same buggy comparison for color-coding, now removed in favor of trusting `place.feasibility` (already computed correctly, per-context) directly.
- **Never send a temporarily closed place to the Routes stage.** Filtering `businessStatus === 'CLOSED_TEMPORARILY'` happens in `normalize-nearby-places.ts`, before local distance ranking or the Route Matrix candidate limit — a closed place must never occupy one of the 3 candidate slots sent to Google Routes, even if it's the nearest result.
- **Home shows one recommendation + two alternates**, not open-ended browsing (MVP). This is specifically a Home-screen rule — the **Nearby** tab (Phase 6) is the deliberate exception: it's a flat browse view of every session candidate, by design, not a violation of this rule.
- **One Places request + one Route Matrix request per nearby-places session, no matter how many screens read it** (Phase 6). Home, Nearby, and Place Details must never fetch independently — they all consume `useNearbyPlacesSession()`, whose `NearbyPlacesSessionProvider` is mounted once at the app root (`app/_layout.tsx`), above the router `Stack`. Do not add a second hook or call site that invokes `placeRepository.findNearby`/`travelTimeRepository.getTravelTimes` — the entire point of the shared session is that there is exactly one. Refresh happens only on first load, a significant device move (>500m), or an explicit `refresh()` call — never on a timer (see "Shared nearby-places session" in [05-technical-architecture.md](./docs/05-technical-architecture.md)).
- **Google Places/Routes are only ever called from a server-side API layer** — never expose unrestricted Google credentials in the mobile client.
- **Stay out of out-of-scope territory** (Quran, Hadith, Zakat, social features, reviews, generic Islamic content, full prayer tracking, complex auth, unnecessary AI features) unless the user explicitly expands scope. See [02-product-requirements.md](./docs/02-product-requirements.md).
- **Accent is the approved forest green** (`#126B46` light / `#6BC69A` dark, see `constants/theme.ts`), used for selection, route, and CTA states against neutral surfaces — not ornamental Islamic-pattern chrome. A small mosque silhouette (`MosqueLogo`) is approved solely as a place-type marker, not devotional decoration. See [04-design-system.md](./docs/04-design-system.md) before changing either.

## Working conventions

- **Expo version**: this project targets Expo **SDK 54**. Per [AGENTS.md](./AGENTS.md), check the versioned docs at `https://docs.expo.dev/versions/v54.0.0/` before writing Expo-related code — do not rely on general/pre-trained knowledge of Expo APIs, since they change across versions.
- **Language**: TypeScript, strict mode (see [tsconfig.json](./tsconfig.json)). Use the `@/*` path alias already configured.
- **Routing**: Expo Router, file-based, under `app/`. Typed routes are enabled. `app/(tabs)/` holds the tab bar (Home, Nearby, Settings); `app/place/[id].tsx` is a stack screen, not a tab.
- **Naming**: existing components use kebab-case filenames (e.g. `haptic-tab.tsx`, `icon-symbol.tsx`) — follow this convention for new files.
- **Don't invent unverified external API details.** An ACJU feed/API's specifics (endpoints, auth, response shapes, pricing/quotas, exact sourcing mechanism) are **not yet verified** in this codebase's docs. Confirm against current official sources before implementing against them — see the "Open verification items" in [06-data-and-api-plan.md](./docs/06-data-and-api-plan.md). **Google Places (New)** and **Google Routes (New)** were both verified 2026-08-21 and are implemented — see [06](./docs/06-data-and-api-plan.md) and [05](./docs/05-technical-architecture.md) for the confirmed endpoints/auth/pricing.
- **Backend**: Supabase (Postgres) is used only where persistence is genuinely needed (shared reference data like timetables/cached places), not as a default for everything.
- **Testing**: `npm test` (Jest + `jest-expo`). Framework-agnostic domain logic (`lib/prayer-times/`, `lib/prayer-places/`, `lib/time.ts`) is kept free of React Native imports specifically so it's easy to test — put new pure logic there, not in components, when it doesn't need to render anything. The one deliberate exception is `hooks/__tests__/nearby-places-session.test.tsx` (component-level, via `react-test-renderer`) — used only because "the shared session Provider is never called twice across navigation" is a React lifecycle property no pure function can express. Don't reach for component tests as a default; this is a narrow, justified exception, not a new general pattern.
- **Prayer-engine layering is a hard rule**: the prayer engine (`lib/prayer-times/prayer-engine.ts`) must only depend on the `PrayerTimeRepository` interface, never on `zone-01.json`, `LocalPrayerTimeRepository`, or any other concrete data source. Adding Zone 02/03/etc. means adding a dataset to `acju-repository.ts`, not touching the engine. No user accounts for MVP.
- **React Compiler is off** (`app.json` → `experiments.reactCompiler: false`) — **do not re-enable without live-device verification.** Found via live testing (2026-08-23) to silently break Home's live per-second countdown tick on a real device while every Jest test for it still passed — Jest never compiles through this experimental Babel transform (no `babel.config.js`; `jest-expo` doesn't read `app.json`'s `experiments` flag), so a green test suite is not evidence a timer/interval-driven UI update actually re-renders in the real app. See the full story in "Client architecture" in [05-technical-architecture.md](./docs/05-technical-architecture.md).

## Current state

Phase 1 (Home UI) is done for now — see [07-roadmap.md](./docs/07-roadmap.md). Further visual changes to Home are paused unless required for functionality. (The original single-route/no-tab-bar decision from this phase was superseded in Phase 6 — see below.)

Phase 2 (real data foundations) is done:
- **Location is real** — `expo-location` requests foreground permission and reads the device's actual GPS coordinates, reverse-geocoded to a place label via the OS's own geocoder (see `hooks/use-device-location.ts`).
- **Prayer times are real** — Zone 01, Aug–Dec 2026, extracted from actual ACJU PDFs and flowing through `PrayerTimeRepository` → prayer engine → `usePrayerTimes()` hook → Home UI (see `lib/prayer-times/` and "Prayer-time architecture" in [05-technical-architecture.md](./docs/05-technical-architecture.md)). Fajr's known end is Sunrise (real ACJU data); Isha's end is honestly `null` (no reliable deadline) rather than borrowed from the next day's Fajr — see the non-negotiable rule above.

Phase 3 (real nearby prayer-place discovery) is done:
- **Prayer places are real** — Google Places (New) Nearby Search, called only from the server-side `app/api/nearby-places+api.ts` route (never from the client), normalized and locally pre-filtered by straight-line distance against the real prayer window (`lib/prayer-places/`). Mock place data (`mocks/home-mock-data.ts`) has been deleted.
- **Live-verified 2026-08-21**: with a real `GOOGLE_PLACES_API_KEY`, the server route returns real, correct mosque results for central Colombo (e.g. Jami Ul-Alfar Mosque, Colombo Grand Mosque).
- **Temporarily closed places are filtered out** (added post-Phase-4, 2026-08-21) — `businessStatus === 'CLOSED_TEMPORARILY'` places are dropped in `lib/prayer-places/normalize-nearby-places.ts`, *before* local ranking or the Routes candidate limit — PrayerStop never sends a Routes request for a place nobody can currently visit. A place with no `businessStatus` at all is kept (missing data isn't evidence of closure); ordinary opening-hours status is still not treated as proof of accessibility — see the non-negotiable rule above.

Phase 4 (real traffic-aware travel time) is done:
- **ETA is real** — Google Routes (New) Compute Route Matrix, called only from the server-side `app/api/route-matrix+api.ts` route (never from the client), for the 3 nearest-by-straight-line-distance candidates only (never the full Places result set — see the non-negotiable rule above). Replaces the Phase 3 straight-line ETA placeholder (`estimateEtaMinutes`, deleted) — `build-place-scenario.ts` and the Home UI needed no changes, since they only ever consumed `etaMinutes` as an opaque number.
- **Live-verified 2026-08-21**: with a real `GOOGLE_ROUTES_API_KEY`, a Route Matrix call against 3 real Colombo mosque coordinates returned real, traffic-aware durations/distances for all 3.
- A destination Google can't route to (`ROUTE_NOT_FOUND`) or that fails individually is dropped, never given a fabricated ETA; if all 3 nearest candidates are unroutable, the app shows a distinct "no reachable prayer places found" state rather than confusing it with "no places exist."
- **Not yet done**: caching (every Home load makes fresh Places + Routes calls — fine for dev/testing, a real cost/latency concern before public launch); coverage outside Colombo/for musallah-type places is still an open spot-check item. See [07-roadmap.md](./docs/07-roadmap.md).

Phase 5 (real recommendation logic & navigation) is done:
- **The recommendation is real end to end** — NOW feasibility (arrival vs. the active prayer's known deadline) and NEXT feasibility (real lead time before the next prayer starts) both run against real Places/Routes data, with a deterministic practicality tiebreak (prefer closer when ETAs are similar; prefer significantly faster when traffic makes the closer option materially slower — see the non-negotiable rule above) for multiple reachable candidates.
- **Fixed a second real bug found via live testing** (see the non-negotiable rule above for the full story): NEXT-mode feasibility no longer compares arrival times against bare `HH:MM` window strings across a possible day boundary — it uses the prayer engine's own day-rollover-safe `secondsUntilNextStart` instead.
- **Navigate is real** — `lib/prayer-places/navigation.ts` opens Google Maps (not Apple Maps) to the recommended place's real Google Place ID, on both iOS and Android, with a web-URL fallback. Kept out of UI components, fully unit-tested.
- **Live-verified 2026-08-21**: the complete flow — real device coordinates → real ACJU prayer state (today's actual date) → real Google Places → real Route Matrix → correct recommendation → correct Google Maps navigation URL — confirmed working end to end in one live run, which is what surfaced the day-rollover bug above.
- No Supabase, auth, backend, notifications, caching, or route-aware (origin→destination) travel yet.

Phase 6 (Nearby/Map, Place Details & shared session data) is done:
- **Shared nearby-places session** — `hooks/nearby-places-session.tsx`, mounted once at the app root. Home, Nearby, and Place Details all read the same fetched data; none fetch independently. See the non-negotiable rule above and "Shared nearby-places session" in [05-technical-architecture.md](./docs/05-technical-architecture.md). The old per-screen `hooks/use-nearby-places.ts` (Phase 3–5) is retired — it would have caused duplicate calls the moment a second screen existed.
- **Bottom tabs**: Home | Nearby | Settings (`app/(tabs)/`). **Place Details** (`app/place/[id].tsx`) is a stack screen, not a tab.
- **Nearby** shows every session candidate as a flat list (not hero+alternates — Home stays the "one recommendation" screen), plus a **Map toggle on iOS only** (`expo-maps`, `AppleMaps.View` — Android needs its own Google Maps SDK API key, not yet configured, so the toggle isn't offered there).
- **Refresh strategy implemented as specified**: reuse while fresh; refetch only on first load, a significant move (>500m), or explicit refresh — never on a timer. Time-based staleness (10 min) only prompts a manual refresh, never triggers one automatically.
- **Live-verified 2026-08-21**: Home, `/nearby`, `/settings`, `/place/[id]` all render correctly via a dev-server smoke test. **Not verified**: the Map view on an actual iOS device/simulator (none available in this environment) — stated honestly, not assumed working.

**Post-Phase-6 Home refinements are done** (2026-08-22, not a numbered phase — see [07-roadmap.md](./07-roadmap.md)):
- **Google Places discovery** now uses `rankPreference: 'DISTANCE'` and requests up to 20 candidates before local filtering (`lib/prayer-places/build-nearby-places-request.ts`) — the local pre-filter-to-3 and Route Matrix cap are unchanged.
- **Location freshness**: location refreshes on app foreground-resume, a manual "Refresh location" control exists on Home, and the nearby-places session only refetches on significant movement (>500m) — the shared-session/no-duplicate-call rule is unchanged. Stale location surfaces as a tappable notice, never a silent auto-refetch.
- **Home prayer card is simplified**: shows only the selected prayer's countdown + key time; ETA/arrival info moved off the prayer card. Sunrise is shown as a small separate note in `PrayerPanel`'s header row, **not** interleaved into `prayer-schedule-strip.tsx`'s per-prayer row — an earlier attempt to interleave it there caused a real UI crash, so that component was reverted to its original, unmodified form. Don't reintroduce Fragment-based row-interleaving there.
- **NOW/NEXT now defaults intelligently**: NEXT/Dhuhr during the Sunrise-to-Dhuhr gap, NEXT/Fajr during Isha (both lack a NOW-mode deadline to plan against), NOW otherwise (`lib/prayer-times/default-planning-context.ts`, `hooks/use-planning-context.ts`). A manual toggle choice is never fought on later per-second ticks — it only resets once the prayer context genuinely changes.
- **Recommendation card has two actions**: primary Navigate (unchanged) and secondary Google Maps (opens the place's own listing via the existing Place ID — `lib/prayer-places/navigation.ts#openPlaceInGoogleMaps`, no extra Places API call). Card trimmed for compactness; recommendation logic itself untouched.
