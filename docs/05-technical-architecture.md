# 05 — Technical Architecture

## Stack

- **App**: React Native + Expo (SDK 54), TypeScript, Expo Router (file-based routing, typed routes enabled).
- **Backend/persistence**: Supabase (PostgreSQL) — used only where persistence is actually needed (see below), not as a default for everything.
- **External APIs**: Google Places API (discovery), Google Routes API (traffic-aware ETA), ACJU published timetables (prayer times source).

> Before writing implementation code, confirm current Expo SDK 54 APIs against the versioned docs at `https://docs.expo.dev/versions/v54.0.0/`, per [AGENTS.md](../AGENTS.md) — the exact `expo-location`, config-plugin, and permission APIs should be verified against that version rather than assumed from general knowledge.

```
┌─────────────────────────┐
│   React Native client    │

│  - Local ranking logic   │

└───────────┬──────────────┘
            │
            ▼
┌─────────────────────────┐        ┌──────────────────────┐
│  Backend layer            │──────▶│  Supabase (Postgres)  │
│  (Supabase + edge funcs,  │       │  - cached place data  │
│   or thin server proxy)   │       │  - ACJU timetable data│
└───────────┬───────┬──────┘        └──────────────────────┘
            │       │
            ▼       ▼
   Google Places   Google Routes
   API              API
```

**Decided:** Google Places and Routes calls go through a server-side API layer — unrestricted Google credentials must never be embedded in the mobile client. This also gives a natural place to enforce the "few candidates only" rule and to add response caching later.

**Resolved 2026-08-21 (Phase 3, extended in Phase 4)**: the server-side layer is an **Expo Router API route** per external API — `app/api/nearby-places+api.ts` (Google Places) and `app/api/route-matrix+api.ts` (Google Routes) — not a separate Supabase Edge Function or standalone server. Expo Router treats any `app/**/+api.ts` file as a server-side handler that runs in a Node/server context — `process.env.GOOGLE_PLACES_API_KEY`/`process.env.GOOGLE_ROUTES_API_KEY` there are never bundled into the client. In local dev this works transparently for both web and native (Expo Go), since the client (`lib/prayer-places/google-places-repository.ts`, `google-route-matrix-repository.ts`) calls them with relative `fetch(...)` resolved against the same dev server. **Production deployment — in progress (2026-08-21)**: chosen target is **EAS Hosting**, since it's Expo Router-native (deploys `+api.ts` routes as real server functions, not just static pages), and reuses the same `eas` CLI/account already needed for EAS Build/TestFlight rather than adding a second hosting vendor. `app.json`'s `web.output` has been changed to `"server"` (required for API routes to be included in the export at all — confirmed locally via `npx expo export --platform web`, which correctly lists both `/api/nearby-places` and `/api/route-matrix` under "API routes"). **Still pending, and blocked on the project owner's own Expo/Apple credentials** (not something this tooling can do on someone's behalf): `eas login`, creating `GOOGLE_PLACES_API_KEY`/`GOOGLE_ROUTES_API_KEY` as **EAS environment variables** (critically, **"Sensitive" visibility, not "Secret"** — Expo's own docs state secrets cannot be deployed with EAS Hosting at all), `eas deploy --environment production`, and then adding the resulting stable URL as `["expo-router", { "origin": "<url>" }]` to `app.json`'s `plugins` array (not yet added, since the URL doesn't exist until after that first deploy). See `eas.json` (added 2026-08-21, standard development/preview/production build profiles) for the EAS Build side of this, and `ios.bundleIdentifier` (`com.ahamedwebstudio.prayerstop`) now set in `app.json`, both prerequisites for EAS Build/TestFlight independent of the hosting question.

## The recommendation pipeline (core architectural constraint)

This is a hard rule from the product spec, not an optimization suggestion:

1. **Discover** — fetch nearby candidate places from Google Places around the user's current location. **Implemented in Phase 3** — see "Prayer-place architecture" below.
2. **Local filter/rank** — score candidates using only local computation:
   - Straight-line (haversine) distance as a cheap proxy for travel time. **Implemented in Phase 3** (`lib/prayer-places/geo.ts`).
   - Reduce the candidate set to a small number before any Routes call. **Implemented in Phase 4**: `selectNearestCandidates` (`lib/prayer-places/select-candidates.ts`) keeps only the nearest **3** by straight-line distance — this is what actually gets sent to Google Routes.
3. **Traffic-aware ETA** — send *only* that short list (3) to Google Routes for real, traffic-aware ETA. **Implemented in Phase 4** — `app/api/route-matrix+api.ts` calls Google's Compute Route Matrix; see "Prayer-place architecture" below and [06-data-and-api-plan.md](./06-data-and-api-plan.md) for the verified endpoint/pricing.
4. **Recommend** — combine traffic-aware ETA and remaining prayer-window time to select the single best-practical option; classify remaining candidates by feasibility status for display as alternates. **Implemented in Phase 5**: `build-place-scenario.ts` computes NOW/NEXT feasibility using the prayer engine's own day-rollover-safe countdown values (not bare `HH:MM` comparisons — see "Prayer-place architecture" below for a real bug this fixed), then breaks ties between multiple reachable candidates by practicality (prefer closer when ETAs are similar; prefer significantly faster when traffic makes the closer option materially slower), not raw distance alone.

**Do not** call Google Routes for every nearby place. This constraint exists specifically for cost and latency control (see [02-product-requirements.md](./02-product-requirements.md)).

## Prayer-time architecture (implemented in Phase 2)

Real ACJU data flows through a strict layering so that adding Zone 02, Zone 03, etc. — or changing where the data comes from — never requires touching the prayer logic itself:

```
ACJU PDFs (assets/images/prayer-times-acju-pdfs/*.pdf)
    ↓  scripts/acju/parse-acju-pdf.js (per month) + build-zone-dataset.js (merge)
data/acju/zone-01.json
    ↓  imported by exactly one file
lib/prayer-times/acju-repository.ts  (LocalPrayerTimeRepository instance)
    ↓  PrayerTimeRepository interface only
lib/prayer-times/prayer-engine.ts    (getPrayerEngineState — pure logic)
    ↓  PrayerEngineState
hooks/use-prayer-times.ts            (ticks every second, exposes NOW/NEXT)
    ↓  PrayerWindow + countdownSeconds
Home UI (app/index.tsx, PrayerPanel, RecommendationHero, AlternatePlaceRow)
```

- **`PrayerTimeRepository`** (`lib/prayer-times/prayer-time-repository.ts`) is the only data-access boundary: `getDailyTimes(zoneId, isoDate)`. `LocalPrayerTimeRepository` is the current in-memory implementation, constructed from bundled zone JSON — but the engine only ever depends on the interface, never on `LocalPrayerTimeRepository` or any JSON file directly. `lib/prayer-times/acju-repository.ts` is the **one** module that imports `data/acju/zone-01.json` and exports a ready-made `acjuPrayerTimeRepository` + `DEFAULT_ZONE_ID` (currently hardcoded to `'01'` — there's no zone-selection UI yet; that's future work once a real-location→zone mapping exists).
- **The prayer engine** (`lib/prayer-times/prayer-engine.ts`, `getPrayerEngineState(repository, zoneId, now)`) determines the active/next prayer and what's actually known about each. It knows nothing about storage — only the repository interface and plain `HH:MM` strings.
  - **Sri Lanka time correctness**: ACJU times are Sri Lanka local time (UTC+5:30, no DST). The engine converts any `Date` via `lib/prayer-times/sri-lanka-time.ts#toSriLankaClock` rather than trusting the device's own timezone — a device set to a different timezone (e.g. a developer's laptop) still gets the correct Sri Lanka date/time-of-day.
  - **Window model — known vs. unknown deadlines (corrected 2026-08-21)**: `PrayerEngineWindow.endTime` is `string | null`, and is only ever a *real* ACJU-derived boundary:
    - **Fajr → Sunrise.** ACJU publishes Sunrise explicitly, and it's Fajr's real, known deadline — this is used directly, not derived from Dhuhr's start. An earlier version of this engine treated Fajr as extending until Dhuhr (informational-Sunrise, no real boundary); that was itself a version of the same mistake described below and has been corrected.
    - **Dhuhr → Asr, Asr → Maghrib, Maghrib → Isha:** the next same-day prayer's start.
    - **Isha → `null`, always.** We have no reliable data on Isha's actual cutoff, mosque closing time, or Jama'ah time — ACJU's basic timetable doesn't state one. **The next day's Fajr is a different prayer's start time, not a stated Isha deadline, and must never be used as one.** An earlier version of this engine made exactly that mistake (`active.endTime = tomorrow's Fajr` when Isha was active) — it silently produced numbers like "539 min remaining" and false "too late to reach" claims every single night. This is now a hard rule enforced by the type (`endTime: string | null`) and covered by explicit regression tests (`lib/prayer-times/__tests__/prayer-engine.test.ts`, describe blocks "Isha never gets a fabricated deadline" and "Fajr uses Sunrise as its real, known end") — **do not reintroduce a fallback that fills `null` from an adjacent prayer's start time.**
    - **The Sunrise-to-Dhuhr gap**: once Fajr's window closes at Sunrise and before Dhuhr actually begins, no prayer window is open. The engine surfaces Dhuhr as the upcoming target (`active.name === 'Dhuhr'`) but marks `hasStarted: false` and reports `secondsUntilActiveEnds: null` — a "starts in"/"starts at" claim is fine (Dhuhr's start time is real), a "remaining" claim is not (Dhuhr hasn't begun). `next` equals `active` in this state, since there's nothing else meaningful to plan for.
  - **`hasStarted`** on `PrayerEngineWindow` is `false` only for this gap case; every other `active` window is a genuinely in-progress prayer. UI code must gate any live "remaining" countdown on `secondsUntilActiveEnds !== null`, never assume it's derivable from `secondsUntilNextStart`.
  - **Midnight/Isha→Fajr**: handled explicitly — before today's Fajr, the active prayer is treated as (yesterday's) Isha (deadline still unknown); at/after today's Isha, the engine looks up *tomorrow's* data purely to report tomorrow's Fajr **start** time (a legitimate "leave by"/"starts in" claim), never as Isha's end. If that adjacent day isn't in the dataset (e.g. past 2026-12-31), the engine returns `{ status: 'unavailable', reason }` rather than fabricating a value.
  - Tested exhaustively in `lib/prayer-times/__tests__/` — a synthetic dataset for controlled edge cases (transitions, the Sunrise gap, midnight wrap, missing-adjacent-day fallback), plus an integration suite against the real bundled Zone 01 data covering the August/September, September/October, October/November, and November/December boundaries, plus a real-data Fajr→Sunrise transition test.
- **`usePrayerTimes()`** (`hooks/use-prayer-times.ts`) is the only thing that ticks — a `setInterval` every second re-evaluates `getPrayerEngineState` from a fresh `new Date()`, so there's no client-side elapsed-time simulation to drift or break on app backgrounding (the Phase 1 mock version had exactly that risk). Exposes `now`/`next` (`{ window, countdownSeconds }`, where `countdownSeconds` is `number | null`) and today's `schedule`.
- **`lib/time.ts#getArrivalOutcome`** returns a discriminated `ArrivalOutcome` (`{status:'known', remaining, overflow, arrivalFraction} | {status:'unknown'}`) rather than always returning numbers — it's `'unknown'` whenever the window's `endTime` is `null`. Every UI consumer (`PrayerPanel`, `RecommendationHero`, `AlternatePlaceRow`) branches on `status` and shows an honest "not available"/"no deadline data" state instead of a computed number when it's unknown. This is the general form of the "distinguish known from unknown" principle — it isn't Isha-specific in the type, only in practice (Isha is currently the only case that produces a `null` endTime).
- **NOW/NEXT default context (added 2026-08-22)**: `lib/prayer-times/default-planning-context.ts#computeDefaultPlanningContext(active)` is a pure function that picks a sensible default `PlanningContext` from the engine's active-prayer identity (`{name, hasStarted}`) — `'next'` during the Sunrise-to-Dhuhr gap (`active.name === 'Dhuhr' && !active.hasStarted`, defaulting toward Dhuhr since no window is open yet to plan a NOW arrival against) and during Isha (`active.name === 'Isha'`, since Isha has no known deadline — see above), `'now'` otherwise. `hooks/use-planning-context.ts#usePlanningContext(active)` wraps this in a `useState`/`useEffect` pair consumed by Home (`app/(tabs)/index.tsx`): the effect's dependency array is `[active?.name, active?.hasStarted]` — **primitive values, not the whole `active` object** — which is what lets a manual toggle selection survive every subsequent per-second re-render (each tick produces a *new* `active` object with the *same* name/hasStarted, so the effect simply doesn't re-fire) while still resetting to the fresh default the moment the prayer context genuinely transitions (e.g. Isha → Fajr, or the Sunrise gap ending when Dhuhr actually starts). Tested at both layers: `lib/prayer-times/__tests__/default-planning-context.test.ts` (pure defaulting logic) and `hooks/__tests__/use-planning-context.test.tsx` (the manual-override-survives-until-genuine-change lifecycle property, via the same `react-test-renderer` "narrow exception" pattern used elsewhere in this project).
- **Resolved in Phase 3, upgraded in Phase 4, corrected in Phase 5**: `PrayerPlace.arrivalTime` is computed live from the real device fix and real Google Places candidates (`lib/prayer-places/build-place-scenario.ts`) — it recomputes whenever the NOW/NEXT context or the underlying candidate list changes. As of Phase 4, `place.etaMinutes` (and therefore `arrivalTime`) is a **real, traffic-aware duration from Google Routes**, not the Phase 3 straight-line estimate. The NOW-context "arrive by X, Y min left" and NEXT-context "leave by X" *display* calculations (`getArrivalOutcome`, `offsetClock` in `lib/time.ts`, consumed by `PrayerPanel`/`RecommendationHero`/`AlternatePlaceRow`) needed no code changes for that upgrade. **However**, live testing in Phase 5 caught a real, separate bug in the underlying *feasibility classification* — see "Prayer-place architecture" below for the fix.

## Prayer-place architecture (Phase 3: discovery; Phase 4: real traffic-aware ETA; Phase 5: real recommendation + navigation)

Mirrors the prayer-time architecture's layering — the UI depends only on interfaces, never on Google Places or Google Routes directly, and neither API key ever reaches the client:

```
Google Places API (New) — Nearby Search
    ↓  POST, server-side only, X-Goog-Api-Key from process.env
app/api/nearby-places+api.ts        (Expo Router API route — the ONLY module that sees GOOGLE_PLACES_API_KEY)
    ↓  normalizeNearbyPlacesResponse() — drops CLOSED_TEMPORARILY places here, before anything else
    ↓  { places: PrayerPlaceCandidate[] } | { error }
lib/prayer-places/google-places-repository.ts   (GooglePlacesRepository — calls OUR route via relative fetch)
    ↓  PrayerPlaceRepository interface only
lib/prayer-places/fetch-nearby-session.ts  ─┬─ selectNearestCandidates()  (local filter: nearest 3 by straight-line distance)
                              │        ↓  DistanceRankedCandidate[] (≤3)
                              │  Google Routes API (New) — Compute Route Matrix
                              │        ↓  POST, server-side only, X-Goog-Api-Key from process.env
                              │  app/api/route-matrix+api.ts   (the ONLY module that sees GOOGLE_ROUTES_API_KEY)
                              │        ↓  { results: TravelTimeResult[] } | { error }
                              │  lib/prayer-places/google-route-matrix-repository.ts  (calls OUR route)
                              │        ↓  TravelTimeRepository interface only
                              └─ applyTravelTimes()  (merge — drops any unroutable candidate, never fabricates)
    ↓  RankedPrayerPlaceCandidate[]  (real distanceKm/etaMinutes/coordinates/routeCondition from Google Routes)
hooks/nearby-places-session.tsx   (Provider, mounted ONCE at app root — see "Shared nearby-places session" below)
    ↓  useNearbyPlacesSession()  (consumed by Home, Nearby, and Place Details — never a second fetch)
lib/prayer-places/build-place-scenario.ts   (pure ranking — context-aware feasibility + practicality tiebreak)
    ↓  PlaceScenario (recommendation + 0–2 alternates, each with real coordinates)
Home / Nearby / Place Details UI
    ↓  onPress
lib/prayer-places/navigation.ts  (openExternalNavigation — opens Google Maps to the real Place ID)
```

- **`PrayerPlaceRepository`** (`lib/prayer-places/prayer-place-repository.ts`) is the discovery boundary: `findNearby(origin, options) → NearbyPlacesResult`. `GooglePlacesRepository` calls `app/api/nearby-places+api.ts`, PrayerStop's own server route, which holds `GOOGLE_PLACES_API_KEY` and performs the actual Google Places (New) `searchNearby` call with `includedTypes: ['mosque']` and `regionCode: 'LK'` (see [06-data-and-api-plan.md](./06-data-and-api-plan.md)). Swapping providers later means writing a new `PrayerPlaceRepository` implementation, not touching ranking or UI.
- **`lib/prayer-places/normalize-nearby-places.ts#normalizeNearbyPlacesResponse`** (added in Phase 4) is the first filter any raw Places result passes through, before local distance ranking or the Route Matrix candidate limit ever run: it drops any place whose `businessStatus` (requested via the field mask) is explicitly `CLOSED_TEMPORARILY` — never send a wasted, metered Routes request to a place nobody can currently visit. A place with no `businessStatus` at all is kept, since missing data isn't evidence of closure. It deliberately does not look at `currentOpeningHours` at all — see the standing constraint in [06-data-and-api-plan.md](./06-data-and-api-plan.md) on why ordinary opening-hours status still isn't a real prayer-accessibility signal.
- **`TravelTimeRepository`** (`lib/prayer-places/travel-time-repository.ts`) is the travel-time boundary, added in Phase 4: `getTravelTimes({origin, destinations}) → TravelTimeMatrixResult`. `GoogleRouteMatrixRepository` calls `app/api/route-matrix+api.ts`, which holds `GOOGLE_ROUTES_API_KEY` and performs the actual Compute Route Matrix call (`travelMode: 'DRIVE'`, `routingPreference: 'TRAFFIC_AWARE'`, field mask `originIndex,destinationIndex,duration,distanceMeters,condition,status`). Also exports `MAX_ROUTE_MATRIX_DESTINATIONS = 3`, enforced both client-side (only 3 candidates are ever requested) and server-side (the route defensively re-caps at 3 regardless of what a caller sends).
- **`lib/prayer-places/select-candidates.ts#selectNearestCandidates`** is the local filter/rank step — pure, framework-free haversine-distance sort, keeping only the nearest `limit` (3) candidates. This runs *before* any Routes call, so the metered API only ever sees a short list, never the full Places result set (non-negotiable rule, see CLAUDE.md).
- **`lib/prayer-places/normalize-route-matrix.ts#normalizeRouteMatrixResponse`** converts Google's raw, positional (`destinationIndex`-keyed) response into our own `placeId`-keyed `TravelTimeResult[]`. An element that errored (`status.code !== 0`), came back `ROUTE_NOT_FOUND`, had a malformed/missing duration, or is simply absent from the response is normalized to an honest `'error'`/`'unreachable'` outcome — never a fabricated duration. Pure and unit-tested independent of the live server route.
- **`lib/prayer-places/apply-travel-times.ts#applyTravelTimes`** merges those outcomes onto the candidates that were actually sent to Routes, producing the final `RankedPrayerPlaceCandidate[]`. Any candidate without an `'ok'` outcome is **dropped entirely** — never shown with a guessed ETA. Real road `distanceMeters` from Routes also replaces the straight-line distance used only for the earlier local pre-filter.
- **`lib/prayer-places/geo.ts`** is now just the pure haversine `distanceKm` — the Phase 3 `estimateEtaMinutes` straight-line placeholder was deleted in Phase 4 since its one caller now gets a real duration from Routes instead.
- **`fetchNearbySession(coords, placeRepository, travelTimeRepository)`** (`lib/prayer-places/fetch-nearby-session.ts`, added Phase 6) is the pure, framework-free extraction of the Places → filter → Routes → merge orchestration above — no React, so it's directly unit-testable with fake repositories. It's called from exactly one place: `NearbyPlacesSessionProvider` (see "Shared nearby-places session" below). This is what makes "one Places + one Route Matrix request per session" enforceable rather than just conventional — there is only one call site in the entire app that can invoke `placeRepository.findNearby`/`travelTimeRepository.getTravelTimes` at all.
- **`buildPlaceScenario(candidates, context, window, countdownSeconds, now)`** (`lib/prayer-places/build-place-scenario.ts`) computes feasibility differently per context, as of Phase 5:
  - **NOW** — unchanged from Phase 3/4: compares an arrival time (computed from `now`) against the *active* window's own start/end via `getArrivalOutcome` (`lib/time.ts`). Safe because `now` and the active window are always the same effective calendar day.
  - **NEXT — corrected in Phase 5 (a real bug caught by live testing)**: previously used the *same* arrival-vs-window-string comparison as NOW, applied to the *next* window. This is wrong whenever the next prayer is tomorrow (e.g. planning for Fajr from late tonight) — comparing "23:50 tonight" against "04:45 tomorrow" as bare `HH:MM` strings silently treats them as the same calendar day, making arrival look *later* than a deadline that's actually many hours in the future, producing a false "too late." Live-testing the full real pipeline (`lib/prayer-places/__tests__/zzz-live-e2e-*`, since deleted after confirming the fix) surfaced this exact case at Isha, planning for tomorrow's Fajr. **Fix**: NEXT now compares real travel time (`etaMinutes`) against `countdownSeconds` — the prayer engine's own `secondsUntilNextStart`, already computed correctly across midnight (see "Prayer-time architecture" above) — never touching the window's `HH:MM` strings at all. `comfortable`/`tight`/`tooLate` now mean "plenty of/tight/insufficient lead time to leave and arrive by the next prayer's start," which is also a more accurate rendering of what NEXT mode is actually for. Regression-tested in `build-place-scenario.test.ts` and `recommendation.test.ts` with the exact tonight→tomorrow-Fajr shape that triggered the bug.
  - Callers pass `context` (Home's NOW/NEXT toggle state; Nearby and Place Details always pass `'now'` — neither has its own NOW/NEXT toggle) and the matching countdown (`timing.countdownSeconds`, already exposed by `usePrayerTimes()`/`selectPrayerTimesForContext` — no new state needed).
  - Two UI components (`RecommendationHero`, `AlternatePlaceRow`) had their own **redundant, independently-buggy** copy of this same comparison for `statusColor` (calling `getArrivalOutcome(window, place.arrivalTime)` unconditionally, including for NEXT). Both now trust `place.feasibility` directly instead — it's already the single, correctly-computed source of truth per context.
  - Isha's "no known deadline" behavior (NOW context) and the practicality tiebreak (`comparePracticality` — prefer closer when real ETAs are within 5 minutes of each other, prefer the significantly faster candidate otherwise) are unaffected by this fix and unchanged since Phase 3/4.
- **`PlaceScenario.alternates` is 0–2 items**, not a fixed tuple — the Phase 4 3-candidate cap plus any dropped-unroutable/closed candidates can genuinely leave 0–2 alternates. Home only renders the alternates section when `alternates.length > 0`; Nearby instead flattens `[recommendation, ...alternates]` into one list, since it's a browse view, not a single-recommendation view (see "Shared nearby-places session" below).
- **Graceful degradation, end to end**: Home, Nearby, and Place Details each derive their own `notice`/`placesNotice` from whichever step hasn't succeeded yet — no coords, a Places-layer problem, or a Routes-layer problem (API error with retry, or the `unreachable` "no reachable prayer places found" case) — and render that in place of the recommendation UI, never a blank or broken card. All three read the exact same underlying session state (`useNearbyPlacesSession()`), so they never disagree about what's currently known. A missing `GOOGLE_ROUTES_API_KEY` surfaces through this same path as a 503 from `route-matrix+api.ts` → an `error` state in the session → each screen's own notice card.
- **Verification status — the complete flow confirmed live 2026-08-21**: real device-location-standin coordinates → real ACJU prayer state (via `getPrayerEngineState`, today's actual date) → real `GET /api/nearby-places` (10 real Colombo mosques) → real `POST /api/route-matrix` (real `ROUTE_EXISTS` durations for the 3 nearest) → `buildPlaceScenario` → a correct, coherent recommendation for both NOW and NEXT — confirming every stage of the real pipeline, not just each API in isolation. This run is exactly what caught the NEXT feasibility bug above (the live state was Isha, with NEXT = tomorrow's Fajr) and confirmed the fix. **Not yet done**: a full visual check of the Home screen itself rendering this live data (would require installing browser-automation tooling not currently in this project — deferred by explicit choice, not a gap in the pipeline).

### Navigation (implemented in Phase 5)

`lib/prayer-places/navigation.ts` opens external navigation for the recommended place — kept out of UI components entirely (`RecommendationHero`'s "Navigate" button just calls `openExternalNavigation(place.coordinates, place.id)`):

- **Google Maps specifically, not the platform default (not Apple Maps)** — a deliberate product choice: Android uses Google's own `google.navigation:q=<lat>,<lng>&mode=d` intent (turn-by-turn driving directions directly in the Google Maps app); iOS and web use Google Maps' universal cross-platform directions URL (`https://www.google.com/maps/dir/?api=1&destination=...`), which hands off to the Google Maps app via iOS universal links if installed, or opens Google Maps in the browser otherwise.
- **Uses the real Google Place ID** (`destination_place_id`, `place.id` — the actual ID returned by Nearby Search, threaded through the whole pipeline once `coordinates`/`id` were added to `RankedPrayerPlaceCandidate`/`PrayerPlace`) alongside the coordinates, so navigation opens the actual named mosque listing (reviews, hours, photos) rather than an anonymous pin.
- **`buildNavigationUrl`/`buildWebNavigationUrl`** are pure, framework-free URL builders (platform passed as a parameter, not read from `Platform.OS` internally) — fully unit-tested without any React Native mocking. `openExternalNavigation` is the only impure part (calls `Linking.canOpenURL`/`openURL`), tested with jest-expo's built-in `Linking` mock: tries the platform-specific URL first, falls back to the universal web URL if it can't be opened (no maps app installed, or an unregistered scheme) or if `canOpenURL` itself throws, and returns whether navigation actually launched.
- No origin is included in either URL — omitting it tells Google Maps to route from the device's current location, matching how both Apple's and Google's own "current location" conventions work.
- **Secondary "Google Maps" action (added 2026-08-22)**: `buildViewPlaceUrl(name, placeId)`/`openPlaceInGoogleMaps(name, placeId)` build and open Google Maps' universal **Search/view-place** URL (`https://www.google.com/maps/search/?api=1&query=...&query_place_id=...`) — genuinely distinct from the directions URL above, verified against Google's Maps URLs documentation. It opens the place's own listing rather than starting turn-by-turn navigation, needs no platform-specific scheme (one URL works identically on iOS, Android, and web via app-link handoff), and uses only the Place ID already present in the current shared nearby-places session — no additional Places API call. `RecommendationHero` renders this as a secondary button next to the existing primary "Navigate" button (`components/home/recommendation-hero.tsx`). Unit-tested alongside the rest of this module in `navigation.test.ts`.

### Shared nearby-places session (implemented in Phase 6)

Phase 6 expanded Home into three screens (Home, Nearby, Place Details) that all need the same nearby-places data. The non-negotiable constraint — **one Places request + one Route Matrix request per session, no matter how many screens read it** — is enforced architecturally, not by convention:

```
app/_layout.tsx
    └─ NearbyPlacesSessionProvider   (mounted ONCE, above the router Stack)
         ├─ useDeviceLocation()       (the one GPS/permission call for the whole app)
         └─ fetchNearbySession()      (the one Places+Routes call site — see above)
              │
              ▼ React Context
    ┌─────────┴─────────┬───────────────────┐
    │  (tabs)/index.tsx  │ (tabs)/nearby.tsx │  place/[id].tsx
    │  (Home)            │  (Nearby)         │  (Place Details)
    └────────────────────┴───────────────────┴───────────────────
    each calls useNearbyPlacesSession() — a context read, never a fetch
```

- **Why React Context and not Zustand/Redux/TanStack Query**: the project has deliberately avoided adding a state-management library so far (see "Data fetching" below), and Context already solves the actual problem here — a Provider mounted once above `Stack`/`Tabs` in `app/_layout.tsx` persists for the whole app session; navigating Home → Nearby → Place Details only mounts/unmounts the screen components *underneath* it, never the Provider itself. The fetch effect inside the Provider only re-runs for its own reasons (first fetch, significant movement, explicit refresh — see below), never because a screen came in or out of view. This is a property of *where the Provider sits in the tree*, not a convention that separate hooks could quietly violate — which is why the old per-screen `useNearbyPlaces` hook (Phase 3–5) had to be retired: if Nearby or Place Details had each called it independently, each would have run its own independent Places+Routes fetch.
- **`hooks/nearby-places-session.tsx`**: `NearbyPlacesSessionProvider` (the one fetcher) and `useNearbyPlacesSession()` (the one consumer hook, throws if used outside the provider). Exposes `{ device, state, isStale, refresh }` — `device` is the single `useDeviceLocation()` instance (so Home/Nearby never trigger a second permission prompt or GPS read), `state` is the session's `NearbyPlacesSessionState` (`idle`/`loading`/`ready`/`empty`/`unreachable`/`error`, mirroring the old per-screen hook's states plus `fetchedAt` on the non-error variants), `isStale` is a display-only signal (see below), and `refresh()` forces a new fetch.
- **Refresh strategy — reuse while fresh, refresh only when appropriate** (the explicit Phase 6 requirement): the Provider's fetch effect refetches only when: (1) this is the first fetch for the current coordinates, (2) the device has moved **significantly** from where the current session was fetched, or (3) `refresh()` was called explicitly. It deliberately does **not** refetch merely because `useDeviceLocation`'s `timestamp` changed (e.g. a `retry()` that returns essentially the same coordinates) — that would defeat "reuse while fresh." There is no timer/polling anywhere in this path — see the non-negotiable "no aggressive background refreshing" rule in CLAUDE.md.
  - **`lib/prayer-places/session-staleness.ts`**: `hasMovedSignificantly(origin, current)` (haversine distance > `SIGNIFICANT_MOVEMENT_METERS`, currently 500m) drives refetching; `isSessionTimeStale(fetchedAt, now)` (elapsed > `SESSION_STALE_THRESHOLD_MS`, currently 10 minutes) drives only the `isStale` *display* flag (Home/Nearby show a small "may be a little out of date" note) — time passing alone never triggers a refetch on its own, only a prompt to refresh manually.
  - The "did a refresh() call actually happen this render" check compares `refreshToken` against a `useRef`-tracked previous value, not `refreshToken > 0` — the latter would keep forcing a refetch on every later, unrelated re-render once any refresh had ever happened. Worth remembering if this logic is ever touched again.
- **`lib/prayer-places/find-candidate.ts`**: `findCandidateById(candidates, id)` — how Place Details looks up "its" place from the shared session's candidate list by Google Place ID (from the route param), instead of needing its own copy of the data. `buildPlaceDetailsPath(placeId)` returns the typed-route destination object (`{ pathname: '/place/[id]', params: { id } }`) Expo Router's typed routes require — the single, tested source of truth for "where does tapping a place go," used by Home's recommendation/alternates and Nearby's list/map alike.
- **Data preserved in the session** (`RankedPrayerPlaceCandidate`, unchanged shape whether read from Home, Nearby, or Details): place ID, name, address (`area`), coordinates, real road distance, real traffic-aware ETA, and `routeCondition` (Google Routes' own condition string, added in Phase 6 — always `'ROUTE_EXISTS'` today since only `'ok'` outcomes reach this type, kept for fidelity/future use, not currently shown in any UI). Feasibility and arrival/leave-by info are deliberately **not** stored in the session — they depend on the current wall-clock time and NOW/NEXT context, so each screen computes them fresh via `buildPlaceScenario` (cheap and pure) rather than caching a value that would go stale the moment a second ticks by.
- **Nearby screen** (`app/(tabs)/nearby.tsx`): always requests the `'now'` context from `buildPlaceScenario` (no NOW/NEXT toggle of its own — Home remains the one place to plan ahead) and flattens `[recommendation, ...alternates]` into a single list — every candidate the session has, shown as a flat browse view rather than one recommendation + alternates. List view reuses `AlternatePlaceRow` (same component Home uses, now with an added optional `onPress`) for visual consistency. Map view is **iOS only** — see below.
- **Map view** (`components/nearby/nearby-map.ios.tsx` / `nearby-map.tsx`): built on **expo-maps** (`AppleMaps.View`), added in Phase 6. Split via the `.ios.tsx`/`.tsx` platform-file-extension convention already used for `icon-symbol` — Android/web never even import the native map module. **Deliberately iOS-only for now**: expo-maps' Android path (`GoogleMaps.View`) needs its own Google Maps SDK API key (a *third* Google credential, separate from Places/Routes) that isn't configured; rather than ship a broken or silently-misconfigured map on Android, the Nearby screen simply doesn't offer the Map toggle there — List is fully functional on every platform. expo-maps itself is alpha and **not available in Expo Go** on any platform — it requires a native/dev-client build, which is not a new constraint for this project since EAS Build was already adopted for TestFlight distribution (see the "Deployment prep" note below). `onMarkerClick` additionally requires iOS 18+ (an expo-maps limitation, not ours); on older iOS the map still renders correctly, marker taps just don't select — List remains the reliable path everywhere.
- **"Selected place"**: tapping a map marker sets a local `selectedPlaceId` (screen-level UI state, not part of the shared session — it's not something Home or Details need to know about) and shows a compact summary card; tapping *that* card opens Place Details. This mirrors common map-app UX (tap pin → preview → commit to details) and is a separate, lighter interaction step than the List view's direct tap-to-Details.
- **Verification**: `hooks/__tests__/nearby-places-session.test.tsx` renders the Provider with `react-test-renderer` (already a transitive dependency — no new test library added) and swaps which consumer is mounted underneath it, simulating Home → Nearby → Place Details navigation, asserting the fake Places/Routes repositories were each called exactly once throughout — this is an intentional, narrow exception to the project's "pure logic only" testing convention, since the guarantee under test is a React lifecycle property that no pure function alone can verify. A live device/simulator run of the Map view itself has not been done (no iOS simulator/device available in this environment) — see [07-roadmap.md](./07-roadmap.md).

## Client architecture

- **Routing**: Expo Router file-based routes under `app/`, typed routes enabled. **As of Phase 6**: `app/(tabs)/` holds the tab bar (`_layout.tsx` using `<Tabs>`) — `index.tsx` (Home), `nearby.tsx` (Nearby), `settings.tsx` (Settings, intentionally minimal — app version only, no accounts/preferences yet). `app/place/[id].tsx` is a stack screen (declared as a sibling `Stack.Screen` to `(tabs)` in the root `_layout.tsx`, not inside the tabs group) — a detail view of something already visible on Home/Nearby, not a fourth tab. Route/Travel and Saved remain reserved, not built.
- **Dependencies added in Phase 1**: `expo-linear-gradient` (abstract `PlaceThumbnail` gradient tile, standing in for a real place photo) and `react-native-svg` (the `RingGauge` circular progress indicator). Both are presentational only — no map/GPS/photo data involved. See [04-design-system.md](./04-design-system.md).
- **Dependency added in Phase 6**: `expo-maps` (Nearby's Map view, iOS only for now — see "Shared nearby-places session" above). Installed via `npx expo install expo-maps`, which added the `expo-maps` config plugin to `app.json` as a bare string entry (no options object) — deliberately left bare so its own `withMapsLocation` plugin logic (which is a no-op unless `requestLocationPermission` is explicitly set) does not touch `NSLocationWhenInUseUsageDescription`, which is already correctly set by the `expo-location` plugin earlier in the `plugins` array. Confirmed by reading `expo-maps`'s installed plugin source directly (`node_modules/expo-maps/plugin/build/withMapsLocation.js`), not assumed.
- **Location — implemented in Phase 2**: `expo-location` requests foreground permission and reads the device's current coordinates via `hooks/use-device-location.ts`. The hook auto-requests on mount (matching the cold-open flow in [03-ux-and-user-flows.md](./03-ux-and-user-flows.md)) and exposes `status` (`idle`/`requesting`/`granted`/`denied`/`error`), `coords`, `address`, `canAskAgain`, and a `retry()` for re-prompting. After a GPS fix, the hook also calls `Location.reverseGeocodeAsync` — this uses the OS's own geocoder (Apple/Google's on-device service via the native SDK), **not** the Google Places/Geocoding *API*, so it doesn't count against the "no Google APIs yet" boundary. The Home header shows that short "neighborhood, city" label (`lib/location.ts#formatAddress`) when reverse geocoding succeeds, falling back to raw coordinates (`formatCoordinates`) if it fails — either way it replaces the old mock location string. Denied/error states are tappable: denied-but-askable re-triggers the permission prompt, permanently-denied opens the OS Settings app (`Linking.openSettings()`), and a fetch error retries. Configured via the `expo-location` config plugin in `app.json` (`locationWhenInUsePermission`); works in Expo Go for foreground use, no dev client required.
- **Data fetching**: **Decided, reaffirmed in Phase 6:** no data-fetching/caching library (e.g. TanStack Query, Zustand, Redux) is introduced. Prayer-time data is bundled locally (no network fetch — see "Prayer-time architecture" above); place data is a real network fetch (`fetchNearbySession`, see "Shared nearby-places session" above) using plain `fetch` + a React Context provider (`hooks/nearby-places-session.tsx`) + `useEffect`/`useState` — sharing across three screens and avoiding duplicate calls turned out not to need a library, just mounting the Provider at the right place in the tree.
- **Local ranking logic**: pure TypeScript, framework-independent (testable without React Native), since it's the core differentiator of the product.
- **React Compiler is disabled** (`app.json` → `experiments.reactCompiler: false`, changed 2026-08-23) — **do not re-enable it without live-device verification first.** It shipped enabled (`true`) from Phase 1 through the Phase 8B countdown work, and was found via live testing to silently break the Home prayer countdown's per-second live tick on a real device (`hooks/use-prayer-times.ts`): the `setInterval`/`setState` loop looked completely correct, and every unit/component test for it passed (including dedicated fake-timer tests asserting it ticks every second) — yet the number never updated on screen once mounted, only recomputing on a full remount. Root cause: **Jest never compiles through `babel-plugin-react-compiler` at all** (there's no project `babel.config.js`, and `jest-expo`'s test transform doesn't read `app.json`'s `experiments` flag the way Metro does for the real bundle), so a compiler-introduced memoization bug in that experimental Babel transform was invisible to the entire test suite and only reproducible on-device. This is the general risk with this flag: **a fully green Jest run is not evidence that a timer/interval-driven live update actually re-renders in the real app** while it's enabled. If re-enabling is ever attempted, verify by watching a live-updating value (e.g. this same countdown) on a real device for at least 10 uninterrupted seconds — passing tests alone proved nothing here.

## Backend architecture

Supabase is used where persistence genuinely matters, not as a blanket requirement:

- **ACJU timetable data**: likely needs to live somewhere queryable/cacheable (Postgres) rather than being fetched live from ACJU on every app open, given ACJU publishes timetables as periodic tables rather than a live API (see [06-data-and-api-plan.md](./06-data-and-api-plan.md) — sourcing format is unverified and flagged there).
- **Place data caching**: caching Google Places results server-side can reduce redundant Places API calls across users/sessions for the same geographic area — a plausible optimization, not committed to for MVP.
- **No user accounts / auth for MVP** — per product requirements, complex authentication is out of scope. Any Supabase usage for MVP is for shared reference data (timetables, cached places), not per-user data.

## Environment & secrets

- **Resolved in Phase 3, extended in Phase 4**: `GOOGLE_PLACES_API_KEY` and `GOOGLE_ROUTES_API_KEY` both live in a local, gitignored `.env` (see `.env.example` for the required shape and setup notes) and are read via `process.env` inside `app/api/nearby-places+api.ts` and `app/api/route-matrix+api.ts` respectively, and only there — Expo Router API routes run server-side, so these values are never bundled into the client JS. No `EXPO_PUBLIC_` prefix is used for either (that prefix is specifically what *would* ship a value to the client). The two keys can be the same underlying Google Cloud API key value as long as both "Places API (New)" and "Routes API" are enabled for it — that's how this was tested — or two separate, more tightly-scoped keys.
- For production, the key should additionally be restricted (by referrer/IP as appropriate for the eventual hosting target) in the Google Cloud Console — not yet done, since there's no production deployment yet (see the Expo Router API route hosting note above).
- Secret-management approach for a real deployment (e.g. EAS Hosting env vars) is still an implementation detail for the build phase.

## Testing

`jest` + `jest-expo` (added in Phase 2) via `npm test`, configured in `jest.config.js`. So far only the pure-logic `lib/prayer-times/`, `lib/prayer-places/`, and `lib/time.ts` modules have tests — no component/screen tests yet. Framework-agnostic domain logic (the prayer engine, repository, geo/ranking math, normalization, time utilities) is deliberately kept free of React Native imports specifically so it stays this easy to test. Both `google-places-repository.test.ts` and `google-route-matrix-repository.test.ts` mock `fetch` to verify each repository only ever calls its own local `/api/*` route, never `googleapis.com` directly — a regression test for the credential-security rule, not just the happy path. `normalize-nearby-places.test.ts` includes a test that a `CLOSED_TEMPORARILY` place is excluded *before* `selectNearestCandidates`'s 3-candidate limit runs — asserting it never occupies a candidate slot even when it would otherwise be the single nearest result. `travel-time-feasibility.test.ts` is an integration-style test proving the real Phase 4 pipeline (`applyTravelTimes` → `buildPlaceScenario`/`getArrivalOutcome`/`offsetClock`) produces correct NOW-arrival, NEXT-leave-by, and Isha-unknown-deadline behavior using realistic Route Matrix output. `recommendation.test.ts` (added Phase 5) runs the *entire* pipeline from raw, Google-API-shaped input (`normalizeNearbyPlacesResponse` → `selectNearestCandidates` → `applyTravelTimes` → `buildPlaceScenario`) rather than any single unit, covering NOW, NEXT, Fajr/Sunrise, Isha, the between-prayers gap, unreachable places, temporarily-closed places, and the practicality tiebreak — including a regression test for the tonight→tomorrow's-Fajr day-rollover bug described above. `build-place-scenario.test.ts` has the same regression at the unit level, plus dedicated NEXT-context tests (comfortable/tight/too-late purely from `countdownSeconds`, independent of window strings). `navigation.test.ts` covers URL construction for iOS/Android/web and the `openExternalNavigation` fallback chain (platform URL → web URL → failure), using jest-expo's built-in `Linking` mock — no real navigation launch is exercised by the automated suite (that requires a real device/simulator), but the pipeline feeding it real coordinates and a real Place ID was confirmed live (see "Verification status" above).

**Phase 6 additions**: `fetch-nearby-session.test.ts` and `session-staleness.test.ts` are pure-function tests (fake repositories, fixed timestamps/coordinates) for the extracted orchestration and staleness/movement logic. `find-candidate.test.ts` covers the place-lookup-by-id and typed-route-destination helpers. `hooks/__tests__/nearby-places-session.test.tsx` is this project's first **component-level** test — a deliberate, narrow exception to "pure logic only," since "the Provider persists across navigation and is never called twice" is a React lifecycle property, not something a pure function can express. It uses `react-test-renderer` (a transitive dependency already present via `react-native`/`jest-expo` — no new test library was added) to mount the Provider, swap its children (simulating Home → Nearby → Place Details), and assert the fake repositories were each called exactly once — plus explicit-refresh and significant-movement refetch behavior, and graceful error handling.

**2026-08-22 additions**: `lib/prayer-times/__tests__/default-planning-context.test.ts` covers the pure NOW/NEXT defaulting rules (Sunrise-to-Dhuhr gap, Isha, and the normal-prayer NOW cases). `hooks/__tests__/use-planning-context.test.tsx` is this project's third component-level test (same justified `react-test-renderer` exception as the location and shared-session hook tests) — it proves a manual NOW override survives repeated re-renders with an unchanged prayer identity, and correctly resets only once the prayer context genuinely transitions. `navigation.test.ts` gained `buildViewPlaceUrl`/`openPlaceInGoogleMaps` coverage — confirming the Search/view-place URL is genuinely distinct from the directions URL and platform-independent, and that opening it never triggers a Places API call.

## What is deliberately not decided here

- Exact caching TTLs for timetable data server-side (the client-side nearby-places session staleness threshold **is** decided — see "Shared nearby-places session" above).
- Android map support (needs its own Google Maps SDK API key — not configured).
- Whether Place Details eventually needs its own data beyond what the shared session already has (e.g. if richer per-place data is ever added, it isn't today per the explicit Phase 6 scope limit).

These are implementation-phase decisions, sequenced in [07-roadmap.md](./07-roadmap.md).
