# Mosque Database — Step 7A: Shared Supabase Backend

Real, tested Postgres schema/RLS/functions for the multi-reviewer mosque
review system — replacing the local single-user JSON/JSONL state (Steps
6A/6B) with a shared Supabase backend. **No PrayerStop runtime app code
touched, no new web UI built** — this is schema + migration + tests only,
exactly as scoped.

## Why this was built and tested against real Postgres, not left as untested SQL

No Supabase CLI or Docker is available in this environment (`supabase`
and `docker` both absent), so `supabase start`'s full local dev stack
wasn't an option. Rather than hand-write SQL and hope it's correct, this
was validated against a **real local PostgreSQL 17 instance** (via
Homebrew, no Docker) with a minimal, faithful stand-in for Supabase's
`auth` schema — see `local-test-harness/README.md` for exactly what's
real vs. simulated, and why the simulated parts are a genuine, verified
reproduction of Supabase's actual mechanism (`auth.uid()`'s exact
implementation, confirmed against Supabase's own source rather than
assumed), not a guess. Every RLS policy, every constraint, and the
concurrent-claim safety guarantee were all exercised for real — see
`tests/`.

## Deploying to a real Supabase project

```bash
# via the Supabase CLI, once you have a project linked:
supabase db push   # applies migrations/0001, 0002, 0003 in order

# the one manual step CLI migrations can't always do — attach the new-user
# trigger to auth.users (run once, in the SQL editor or via psql):
psql "$DATABASE_URL" -f local-test-harness/0001_wire_auth_trigger.sql
# (that file's SQL is real and correct for production use — only its
# location under local-test-harness/ is about file organization, not about
# the trigger itself being test-only)

# one-time data import:
python3 scripts/migrate_to_supabase.py
psql "$DATABASE_URL" -f output/migrate_data.sql
```

## Running the tests locally

Requires PostgreSQL (`brew install postgresql@17`, no Docker needed):

```bash
brew services start postgresql@17   # or: pg_ctl -D /opt/homebrew/var/postgresql@17 start
bash tests/run_all_tests.sh
```

Rebuilds `prayerstop_mosque_test` from a clean slate every run (drops and
recreates the database), so it's always testing the migrations as they'd
apply to a fresh project, not accumulated local state.

## Schema summary

| Table | Purpose | RLS |
|---|---|---|
| `reviewers` | 1:1 with `auth.users`; `role` is `reviewer` or `admin` | own row only; admin sees all |
| `mosque_records` | Master dataset (mirrors `master-dataset.json`) | any authenticated reviewer reads all (not private data) |
| `review_tasks` | Claim/assignment state machine | unclaimed tasks visible to all; claimed/completed visible only to the assignee; admin sees all |
| `review_decisions` | Append-only audit log | own decisions only; admin sees all |

No table has a direct client `INSERT`/`UPDATE`/`DELETE` grant for
`authenticated` — every mutation goes through `claim_review_task()`,
`complete_review_task()`, `skip_review_task()`, or `log_review_note()`
(all `SECURITY DEFINER`, all enforcing the business rules explicitly in
code — see `0003_functions.sql`'s header comment for why RLS
`USING`/`WITH CHECK` alone is the wrong tool for a multi-step claim state
machine).

See `report.md` for the full write-up: schema rationale, migration
counts, and every test's result.
